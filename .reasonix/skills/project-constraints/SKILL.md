# Project Constraints（LLM）

## 1. 何时调用（强制）
- 每次开始任何**项目代码开发任务**时，大模型必须强制优先调用该技能。
- 任何涉及项目代码改动（新增/修改/删除文件）、依赖变更、业务配置调整时
- 任何涉及 UI 方案选择（组件库、弹窗/抽屉、表格、图表）时
- 任何可能需要新建业务组件、hooks、工具方法或模块 README 时

以下任务默认不触发本 Skill：
- 对话问答、纯分析、纯 review、概念解释
- 文档阅读、文档总结、纯文档修改
- `workflow/`、仓库流程脚本、仓库规则文档改动
- 其他不涉及项目代码改动/生成的工作

## 2. 核心原则（必须遵守）
1. 只做用户要求的事，不做“顺手优化”
2. 不确定就说“无法实现”，并说明缺少的关键信息（不得猜测）
3. 不编造库、不编造 API、不假设仓库里存在某个依赖或封装
4. 安全优先：不生成恶意代码、漏洞、爬虫；不引入泄密/越权/注入风险
5. 保持功能不变：优先最小改动，避免破坏已有行为与对外接口。**在没有明确要求的前提下，绝不私自删除或隐藏已有的功能（按钮、菜单、快捷入口等）。如果发现隐含的错误或冗余逻辑，必须先提示用户，由用户决定是否修改/删除。**
6. 设计与开发必须同时考虑 Web 端与 iPad（平板）适配性（布局、交互、触控、横竖屏）
7. 设计与开发必须同时考虑日间模式与夜间模式两种主题切换（颜色、对比度、阴影、图片/图标在深色背景下的可读性）
8. 使用 antdv-next 组件时不得为暗色/亮色主题做额外覆盖（组件已内置适配）；仅在自研业务组件时需要兼容日夜间主题
9. 一旦涉及 try/catch/finally 的异步错误处理代码生成，必须使用 await-to-js（to）风格实现，避免散落的 try/catch
10. 书写代码时，所有标签必须闭合（包括 HTML/JSX/Vue template、JS/TS 代码块、CSS/SCSS 等任何上下文），禁止出现未闭合的标签

## 3. 输出与表达规范

### 3.1 输出格式
- 只输出【可直接运行】的代码
- 代码必须用 \`\`\`language 包裹
- 先给最终代码，再简要说明
- 步骤必须用 1/2/3
- 禁止大段文字
- 禁止冗余解释

### 3.2 代码要求
- 代码必须带注释（解释“为什么这么做/边界是什么”，避免无意义注释）
- 必须使用最新语法，生成 vue 文件时需满足 Vue 3.4+ 最简洁优雅的写法（例如优先使用 `defineModel`、`defineOptions` 等）
- 状态声明统一使用 `ref`，严禁使用 `reactive`，以避免解构或重新赋值时丢失响应式
- 遇到大量的复杂逻辑，必须将其抽象为单独的 hook（Composable），让 UI（Vue 模板）和逻辑尽量分离，使页面组件退化为纯粹的布局组合器
- 必须遵循行业最佳实践

## 4. UI 与交互（优先级规则）

### 4.1 组件库与封装优先级
- 组件库：优先使用 `antdv-next`，避免引入或回退到 `ant-design-vue`
- **组件使用规范 (强制)**：在使用 `antdv-next` 的组件时，**必须**阅读该 skill (`antdv-next`) 以及相关的 LLM 文档（如 `references/docs/vue/` 和 `references/components/` 下的文件），严格遵循其最新的 API 规范（Props、Events、Slots）使用组件，避免使用已废弃的写法。
- 组件封装：优先使用项目内既有封装组件（例如 `@decision-core/*`、`@decision/*`）
- 新增组件前必须全局检索是否已有同类组件/封装，避免重复建设

### 4.2 弹窗 / 抽屉
- 尽量使用 `vue-modal-provider`
- 若项目已有弹窗/抽屉封装 hooks 或组件，优先使用封装版本，避免重复实现挂载/状态管理

### 4.3 表格 / 列表
- 生成表格（含查询、分页、排序、筛选联动）时，尽量使用 `use-table-query`
- 若项目已有更高层表格封装/适配（例如统一的 table 组件或 vxe-table 适配），优先在封装上对接 `use-table-query`

### 4.4 图表（ECharts）
- 尽量使用 `use-echarts`（hooks）与 `common-echarts`（通用图表组件）
- 避免在业务页面直接手写 ECharts 初始化/销毁逻辑

## 5. 组件演进策略（改旧 vs 新建）
- 若现有组件通过少量、清晰的扩展即可满足需求：优先在不影响已有功能的前提下改造已有组件
- 若改造会让组件变得十分复杂且难以理解/使用：新建新的组件或 hooks，并保持与现有封装的接口风格一致

## 6. 组件架构设计原则（10 条）

### 6.1 单一职责（SRP）
- 一个组件只做一件事，并把它做好
- 推荐分工：
  - 页面组件 = 布局 + 数据获取
  - 业务组件 = 某块业务逻辑
  - UI 组件 = 纯展示

### 6.2 单向数据流（Props Down, Events Up）
- 数据从上往下流，事件从下往上抛
- 禁止子组件直接修改父组件状态

### 6.3 可复用性优先
- 能复用的绝不写两遍
- 通用 UI 抽成基础组件；通用逻辑抽成 Hook/Composable；业务相似抽业务组件
- 判断标准：复制粘贴超过 2 次就必须抽离

### 6.4 高内聚、低耦合
- 内聚：相关逻辑放一起
- 耦合：组件之间依赖尽可能少
- 推荐分层：
  - 页面组件 → 业务组件 → UI 组件 → 基础组件

### 6.5 显式优于隐式
- 接口清晰，不搞“魔法”
- Props 明确，必填/可选清晰；事件名语义化
- 不依赖全局隐式状态；TS 类型必须完整

### 6.6 组件分层（核心架构原则）
业务模块需要遵循组件分层的思想，但不需要强制凑齐 4 层。
满足这三层就足够：
- 基础组件：公共 UI（必须有）
- 业务组件：模块内复用单元（必须有）
- 页面组件：入口容器（必须有）

### 6.7 容器与展示分离
- 容器组件：管数据、请求、状态
- 展示组件：只管渲染、样式、交互
- 好处：易测试、易复用、易维护

### 6.8 不可变性 & 状态最小化
- 状态只保留核心数据，派生数据用计算属性
- 避免冗余状态；复杂状态用 store/pinia 管理(一般不用全局状态，如果一定要用，需要补充必须这么做的理由和原因)

### 6.9 可预测、可测试
- 相同输入 → 相同输出
- 减少副作用，逻辑尽量纯函数化，便于单测/回归

### 6.10 可访问性 & 扩展性
- 支持插槽、配置、样式覆盖，结构可扩展不写死
- 语义化标签与 a11y 友好

## 7. 接口层（API）设计规范

### 7.1 RESTful
- 接口设计需要遵循 RESTful 语义（资源导向、HTTP 方法语义清晰、路径命名一致）

### 7.2 命名约定
- 接口层函数名必须以 `Api` 作为后缀结尾（例如 `getUserApi`、`createOrderApi`）

### 7.3 注释要求
- 每个 API 函数必须有详细注释，描述：
  - API 的作用与业务场景
  - 关键参数含义与边界条件
  - 返回值结构与错误处理约定

### 8.1 模块文档（按菜单项）
- 每个菜单项对应一个模块；每个模块目录必须存在 `README.md`
- 模块 `README.md` 至少包含：
  - 模块概览：功能边界、用户角色、主要场景
  - 组件设计：组件树结构、职责划分、状态归属
  - 数据流：请求来源、状态管理、缓存策略、错误处理
  - 依赖与封装：`vue-modal-provider`、`use-table-query`、`use-echarts`/`common-echarts`、`antdv-next` 与项目封装组件用法
  - 交互与可用性：键盘操作、无障碍提示、响应式、性能注意事项
  - 集成与扩展点：对外 props/事件、插槽、可扩展接口
  - 注意事项：边界条件、已知限制、常见坑
  - 示例与最佳实践：典型用例与代码片段

### 8.2 新增组件 / hooks
- 若新建组件或 hooks：必须在同目录补充详细 `README.md`（用途、使用方式、输入参数、返回值/事件、最佳实践、限制）

### 8.3 工具方法
- 工具类方法必须有清晰的功能注释（函数说明、参数/返回、边界与异常行为）

## 9. 变更边界
- 不为“顺手优化”修改与当前需求无关的样式、依赖、工具链、配置或代码格式
