## 候选沉淀点

### 1. props 对象整体替换后直接解构丢失响应式（推荐，state/vue3 domain）

**现象**：父组件通过 `stockingValues.value = newObj` 整体替换 ref 值，子组件用 `const { stockingValues } = props` 直接解构后，模板读到的是**替换前的旧对象引用**，显示「没有数据」。

**根因**：`applyDetailTableValues` 整体替换 ref.value（`stockingValues.value = rawValues`），props 更新为新对象；但子组件 script 直接解构拿到的是**旧引用**（解构在 setup 时执行一次）。模板直接访问 props 名则始终最新（Vue 自动解包）——所以区域平衡正常、库存异常。

**解法**：子组件用 `toRefs(props)` 响应式解构，或模板直接访问 props 名不在 script 解构：

```ts
// ❌ 解构一次后固定旧引用，父级整体替换 ref 值后失效
const { stockingValues } = props;

// ✅ toRefs 保持响应式，始终指向 props 最新值
const { stockingValues } = toRefs(props);
// 模板中自动解包：stockingValues[region][material]
```

**注意事项**：
1. `vue/no-mutating-props`：直接改 `props.xxx` 报错；`toRefs` 解构后改 `ref.value` 内部属性不报（且语义是写回父级共享响应式对象）
2. 若改为 emit 更新（单向数据流）更规范，但对 composable 共享 ref 对象场景，toRefs + 改属性是务实解

## 推荐理由

「父级整体替换 ref 值 + 子组件直接解构 props 丢响应式」是 Vue 3 高频坑，本仓库之前也踩过类似（composition-api.md 有 defineProps 相关），值得沉淀补充此变体。
