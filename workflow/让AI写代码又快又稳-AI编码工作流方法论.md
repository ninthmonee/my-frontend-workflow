# 让 AI 写代码又快又稳 —— AI 编码工作流方法论

> 本文是**方法论层**文档：只讲"为什么这样做、解决什么问题、代价是什么、如何借鉴"，
> 不含任何具体命令、路径与实现细节。
> 适用对象：想在团队/项目中引入 AI 编码代理（Agent）协作机制的任何人。
>
> 配套文档：[让AI写代码又快又稳-AI编码工作流设计详解.md](./让AI写代码又快又稳-AI编码工作流设计详解.md)

## 1. 要解决的问题：AI 编码代理的五类事故

AI 代理写代码在真实项目中反复出现五类事故，这套方法论就是针对它们的：

| 事故 | 典型表现 | 后果 |
|---|---|---|
| 乱改 | 让改一个字段，顺手重构整个文件 | 代码审查成本飙升，引入无关风险 |
| 假通过 | 说"typecheck 过了"，实际没跑或报错被忽略 | 上线后才发现编译/类型错误 |
| 不可恢复 | 会话一关，改到哪一步全忘了 | 重复劳动，或带着半成品提交 |
| 经验流失 | 上次踩的坑，换个说法又问一遍 | 同类错误反复发生 |
| 无边界 | 代理无法判断该改什么、不该改什么 | 越界修改、破坏既有约定 |

核心判断：**问题不在"提示词写得不够好"，而在缺少流程机制**——代理的行为
需要被约束、代理的产出需要被验证、关键决策需要人来拍板。

## 2. 核心主张

一句话：**让 AI 写代码从"坐过山车"变成"坐高铁"——又快又稳。**

- **快**：计划先对齐、验证自动跑、断点可续跑，减少返工与重复沟通；
- **稳**：物理拦截越界、证据保证真实、人在关键点确认，产出可信可审计。

## 3. 五大机制（设计原则）

每一条机制解决第 1 节中的一类或多类事故：

| # | 机制 | 是什么 | 解决哪类事故 |
|---|---|---|---|
| 1 | **物理门禁，而非口头纪律** | 计划未通过前，代理对源码的编辑/写入被**系统直接拒绝**（exit 2），不是"建议别改" | 乱改、无边界 |
| 2 | **证据驱动，禁止空口通过** | 每个阶段有落盘证据，关卡推进前自动校验证据完整性，无法"空手过门" | 假通过 |
| 3 | **人机确认点** | 计划、改动、验收、沉淀四个决策点必须由**人**确认；代理禁止代替用户确认 | 乱改、无边界 |
| 4 | **最小改动** | 决策阶梯强制"最简方案命中即停"：YAGNI → 标准库 → 浏览器原生 → 已装依赖 → 项目封装 → 一行 → 最小实现，禁止预先抽象与顺手优化 | 乱改 |
| 5 | **可恢复、零依赖** | 状态自动备份、损坏自愈、断点续跑；运行时零依赖，无供应链风险 | 不可恢复 |

## 4. 怎么算生效（成功标准）

这套机制是否真正生效，可用以下标准检验：

- 一次完整流程走完后，每次改动目录下有完整的分阶段证据，且关卡全部通过；
- 计划未通过时，对源码的任何编辑都被拦截（可复现验证）；
- 会话中断后重开，代理能从状态文件恢复到正确阶段，无需重新解释需求；
- 任意改动（含微小改动）完成后，验证命令真实通过，且有"是否沉淀经验"的询问记录。

## 5. 明确不做什么（非目标）

- 不替代代码审查（不替代人 review）；
- 不做 CI/CD 或发布系统；
- 不做跨宿主强一致（物理门禁只在支持拦截能力的宿主生效）；
- 不自动写业务逻辑（业务决策仍由人确认）。

## 6. 关键权衡（决策时取舍了什么）

| 决策 | 理由 | 代价 |
|---|---|---|
| 物理拦截而非纯纪律 | "建议别改"对 LLM 无效，物理拦截才可靠 | 依赖宿主支持；不支持的宿主退化为纪律模式 |
| 证据文件驱动关卡 | 可审计、可恢复、防"空口通过" | 每个阶段多一次文件写入 |
| 人机确认（多次） | 关键决策必须人拍板 | 流程变"重"——用分级响应缓解 |
| 分级响应 | 微小改动走轻量路径，复杂改动走完整流程 | 需要一套分级判定规则（看质、看量） |
| 验证首失败即停 | 快速反馈，避免错误级联 | 一轮只暴露一个错误 |
| 回退有纪律 | 错误暴增按文件回退，多轮不通全量丢弃 | 丢失部分修改（但保住工作区干净） |
| 失败分析独立 | 由只读角色判定"可自动修 / 需人工"，避免代理在业务逻辑上瞎改 | 多一次分析开销 |
| 危险操作无条件拦截 | 轻量路径也不豁免危险命令（删库、强推等） | 用户需确认后重试 |
| 沉淀必须询问 | 经验不沉淀就流失；但**未经确认禁止自行写入**知识库 | 每次改动多一次询问 |

## 7. 收益

### 对开发者个人
- **少返工**：计划确认后才动手，方向错了在改代码前就被拦下；
- **少背锅**：证据链完整，"为什么这么改"有据可查；
- **少重复**：经验库去重沉淀，同类坑只踩一次；
- **断点续跑**：会话关掉再打开，状态自动恢复。

### 对团队
- **统一纪律**：所有代理走同一套流程，行为可预期；
- **可审计**：每次改动有独立证据，code review 时可对照计划范围检查是否越界；
- **知识资产化**：经验库随使用持续增长，新人/新代理可检索复用。

### 对代码质量
- **验证真实发生**：构建、格式化、lint、类型检查自动执行且结果落盘，无法"假装通过"；
- **错误分类处理**：区分"可自动修"与"需人工"，避免代理在业务逻辑上瞎改；
- **回退有纪律**：错误暴增按文件回退，不把半成品留给仓库。

## 8. 代价与适用边界

### 时间成本
- 复杂改动需要多次人工确认（计划/改动/验收/沉淀），每次审阅约数分钟；
- 微小改动也有少量固定开销（验证 + 沉淀询问），但显著低于其防住的返工成本。

### 不适合这套机制的场景
- 一次性脚本、临时实验（走流程反而拖慢）；
- 纯问答、读代码、分析架构（不触发工作流）；
- 非 git 项目（证据依赖 diff 能力，会退化）；
- 修改工作流自身文件（豁免，不需要套流程管流程）。

## 9. 借鉴清单（想把这套方法论引入自己的团队时）

1. **先确认验证命令可脚本化**：build / typecheck / lint 能一行跑完，否则"验证真实发生"无从谈起；
2. **分两级起步**：微小改动走轻量路径，复杂改动走完整流程（分级标准：先看"质"——动了哪些模块与契约，再看"量"——行数与文件数）；
3. **把规则写进一份代理行为契约文档**（约定代理什么时候必须走流程、每个阶段做什么、禁止做什么）；
4. **强制关键确认点**：计划、改动、验收三处必须人工确认，代理不得自答；
5. **要求证据落盘**：每个阶段的产物有文件记录，关卡推进前自动校验，缺证据不许过；
6. **建立沉淀机制**：每次改动完成后必须问"值不值得沉淀"，写入前先查重（按领域/场景/方案/关键词），更新索引，避免知识库变垃圾场；
7. **按宿主能力决定拦截强度**：能物理拦截的宿主用硬门禁，否则靠契约 + 评审抽查兜底；
8. **先小范围试点再推广**：挑 1~2 个真实需求跑通全流程，验证收益后再定团队规范。
